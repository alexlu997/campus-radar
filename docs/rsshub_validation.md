## 可核实的源码行为

以下来自[官方固定提交的路由源码](https://github.com/DIYgod/RSSHub/blob/1d73c7c6158e0fe2bfab06300f41b040716127ab/lib/routes/sjtu/cs/xshd.tsx)，与运行实测分开。原文及来源元数据保存在[`outputs/rsshub-check/source/`](../outputs/rsshub-check/source/)。

- 列表固定读取CS官网`/xshd.html`，用`ofetch`和Cheerio解析`.ny-con .u12 > li`；该路由没有翻页遍历。单次条数由上游首页决定。
- “举办时间”来自列表中的`时间：`文本，放在description内；地点和主题也来自列表。它没有输出独立结构化的活动开始、结束字段。
- `pubDate`来自微信文章日期或普通详情正文的发布日期。普通详情的纯日期字符串被按`+0000`解析；这是源码采用的日期表示，不能当作活动时刻，也不能据此得知精确发布时刻。
- 详情缓存键为`sjtu:cs:activity:v4:{item.link}`。详情异常可降级为列表信息，保留标题、链接、活动时间等，但可能没有正文和`pubDate`。
- 特定`WeChatMpError`在详情缓存回调内部被捕获，回调随后可返回空正文、空日期；实际是否发生、空结果是否留存以及缓存时长，本轮未验证。
- 路由声明不需要Puppeteer。其首个实际依赖仍是CS上游可达；添加本地RSSHub实例不会消除本次已观测的上游TLS握手失败。

## 复跑方式与停止点

在仓库根目录执行：

```sh
python3 tools/check_rsshub.py --self-test
python3 tools/check_rsshub.py
```

脚本只做两个URL的直连/显式代理对照，各一次。每次设8秒连接超时、25秒总超时、10MiB响应上限，正常校验证书，保存原始响应。只有获得有效feed时才重复一次同模式feed请求以供缓存对照。输出目录按UTC时间新建，不覆盖前次证据。脚本成功退出表示诊断记录已生成，是否取得feed应读取汇总中的`valid_feed`和HTTP状态。

脚本自检已通过：正常RSS可计数，缺少日期保持空值，HTML拒绝页与损坏XML不会被误判成零条RSS。即使响应头为HTTP 200且留下可解析XML，curl传输失败也不计作有效feed；失败响应体仍保留用于诊断。此修复以模拟传输结果验证，没有重复真实请求。

本轮在**公开实例明确拒绝 + 本机CS上游TLS失败**处停止，没有安装整套RSSHub或启动长期服务。继续验收所需的前提是得到一条正常可访问CS上游的执行路径，并使用允许该路由请求的RSSHub实例；之后才能读取真实feed，逐条对照列表与详情，再检验日期、正文和缓存。现有结果不支持“RSSHub已可用”或“该路由已经失效”这两种结论。
